4.4.   Hasil Pengujian

Pengujian sistem dilakukan menggunakan metode black-box testing yang dirancang untuk memvalidasi kebenaran fungsional algoritma FIFO serta konsistensi data antar-tabel. Pengujian difokuskan pada tiga aspek kritis, yaitu validasi algoritmik FIFO, verifikasi konsistensi stok, dan validasi jejak audit. Seluruh skenario pengujian dieksekusi pada lingkungan lokal menggunakan XAMPP dengan MariaDB 10.4.32 dan PHP 8.0.30.

4.4.1.   Pengujian Algoritmik FIFO

Skenario pengujian dirancang dengan memasukkan beberapa batch masuk untuk satu barang yang sama pada tanggal yang berbeda, kemudian melakukan pengeluaran dengan variasi jumlah permintaan. Sistem diharapkan selalu memproses batch tertua terlebih dahulu, melakukan konsumsi parsial jika batch tidak mencukupi, dan menolak transaksi jika total stok tidak memadai. 4.5.   Pembahasan

Bagian ini membahas analisis mendalam terhadap hasil penelitian dan pengujian yang telah dilakukan, meliputi interpretasi temuan, identifikasi hambatan yang dihadapi selama pelaksanaan penelitian, serta rekomendasi untuk pengembangan selanjutnya.

4.5.1.   Analisis Implementasi Algoritma FIFO

Implementasi algoritma FIFO pada sistem ini dilakukan sepenuhnya pada layer aplikasi menggunakan PHP/CodeIgniter, bukan pada layer basis data. Pendekatan ini dipilih karena memberikan fleksibilitas yang lebih tinggi dalam menangani skenario konsumsi parsial, di mana satu permintaan pengeluaran dapat mengonsumsi stok dari beberapa batch secara berurutan. Logika FIFO bekerja dengan mengambil seluruh batch aktif (qty_sisa > 0) yang diurutkan berdasarkan created_at ASC, kemudian melakukan iterasi pengurangan qty_sisa pada setiap batch hingga permintaan terpenuhi. Setiap pengurangan dicatat melalui kolom from_batch_id pada tabel as_history, sehingga jejak penelusuran batch dapat dipertahankan secara lengkap.

Dari hasil pengujian pada Tabel 4.1, algoritma FIFO terbukti mampu menangani tiga skenario kritis secara konsisten: konsumsi batch penuh ketika jumlah batch mencukupi, konsumsi parsial lintas batch ketika satu batch tidak cukup, dan penolakan transaksi ketika total stok tidak memadai. Keunggulan pendekatan ini dibandingkan metode dekrementasi stok tunggal (single-stock decrement) adalah kemampuan sistem untuk menyajikan informasi batch mana yang sedang dikonsumsi, kapan batch tersebut diterima, dan berapa sisa stok per batch — informasi yang sangat berharga untuk keperluan audit dan traceability.

4.5.2.   Analisis Konsistensi Data dan Integritas Referensial

Konsistensi stok antara tabel as_history dan as_electric dijaga melalui mekanisme sinkronisasi otomatis yang dieksekusi setelah setiap transaksi. Hasil pengujian pada Tabel 4.2 menunjukkan bahwa mekanisme SUM(qty_sisa) berhasil menjaga akurasi stok pada seluruh skenario, termasuk setelah operasi audit adjustment. Pendekatan ini lebih andal dibandingkan penyimpanan stok tunggal pada kolom as_electric, karena tabel as_history berfungsi sebagai single source of truth yang merekam seluruh mutasi stok secara kronologis.

Namun demikian, terdapat catatan penting terkait integritas referensial. Pada skema basis data aktual, tidak seluruh foreign key memiliki constraint CASCADE yang konsisten. Misalnya, relasi as_history.user_nik ke as_user.nik tidak memiliki constraint foreign key formal, sehingga penghapusan data pengguna secara manual berpotensi menimbulkan orphan record pada tabel riwayat. Hal ini menjadi area perbaikan yang perlu ditindaklanjuti pada pengembangan selanjutnya.

4.5.3.   Hambatan dan Tantangan Penelitian

Selama pelaksanaan penelitian, beberapa hambatan dan tantangan yang dihadapi meliputi:

Pertama, keterbatasan data awal dari perusahaan. Data yang diperoleh dari PT. Apparel One Indonesia hanya berupa file Excel yang berisi nama barang, merek, spesifikasi teknis, dan jumlah stok awal tanpa informasi riwayat transaksi historis. Akibatnya, pengujian FIFO harus dilakukan dengan data sintetis yang dibuat secara manual, sehingga hasil pengujian belum sepenuhnya merepresentasikan kompleksitas data produksi nyata.

Kedua, tidak adanya mekanisme pencegahan race condition pada basis data. Ketika dua pengguna melakukan transaksi pengeluaran secara simultan untuk barang yang sama, terdapat kemungkinan konsumsi batch yang tumpang-tindih karena tidak adanya implementasi locking mechanism (seperti SELECT FOR UPDATE) pada query pengambilan batch. Pada lingkungan produksi dengan banyak pengguna aktif, hal ini berpotensi menyebabkan inkonsistensi stok sementara.

Ketiga, arsitektur sistem yang masih bersifat monolitik dan berjalan pada server lokal (XAMPP). Sistem belum diimplementasikan pada lingkungan produksi dengan server dedicated, sehingga aspek performa seperti response time query, ketahanan terhadap beban tinggi, dan skalabilitas belum dapat diukur secara representatif.

Keempat, pengujian dilakukan secara manual melalui black-box testing tanpa menggunakan framework automated testing. Meskipun seluruh skenario berhasil divalidasi, pendekatan manual ini kurang efisien untuk pengujian regresi ketika terjadi perubahan kode atau penambahan fitur baru di masa mendatang.

4.5.4.   Rekomendasi Pengembangan Selanjutnya

Berdasarkan temuan dan hambatan yang telah diidentifikasi, berikut adalah rekomendasi untuk pengembangan sistem pada tahap selanjutnya:

Pertama, implementasi mekanisme database locking menggunakan SELECT FOR UPDATE pada query pengambilan batch FIFO untuk mencegah race condition pada lingkungan multi-pengguna. Pendekatan ini akan menjamin bahwa batch yang sedang diproses oleh satu transaksi tidak dapat diakses secara bersamaan oleh transaksi lain.

Kedua, penambahan constraint foreign key formal dengan aturan ON DELETE dan ON UPDATE CASCADE pada seluruh relasi antar-tabel untuk menjamin integritas referensial secara menyeluruh di level basis data.

Ketiga, migrasi sistem ke lingkungan produksi menggunakan server dedicated atau cloud hosting untuk mengukur performa sistem secara representatif, termasuk response time query FIFO di bawah volume data ribuan record dan ketahanan sistem terhadap akses konkuren.

Keempat, pengembangan modul automated testing menggunakan framework seperti PHPUnit untuk mengotomasi pengujian regresi, sehingga perubahan kode di masa mendatang dapat diverifikasi secara cepat dan konsisten tanpa bergantung pada pengujian manual.

Kelima, penambahan fitur notifikasi otomatis (email atau dashboard alert) ketika stok suatu komponen mencapai batas minimum, sehingga Admin Gudang dapat melakukan pemesanan ulang (reorder) secara proaktif sebelum terjadi kekurangan stok yang mengganggu operasional produksi.
